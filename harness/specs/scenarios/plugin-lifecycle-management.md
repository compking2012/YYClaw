Plugin lifecycle management covers bundled and external plugins as one system with different source types. The core model has two layers:

- `PluginPackage`: a discoverable, installable, upgradable, and recoverable package with identity, version, source, manifest, install location, and validation state.
- `PluginCapability`: an integration surface declared by a package, such as a channel, provider, skill, or runtime extension.

Lifecycle stages:

- Declare: plugin manifests describe package identity, source expectations, compatibility, and provided capabilities.
- Discover: ClawX scans bundled and external sources and produces a factual inventory. Discovery does not choose active owners.
- Resolve: ClawX chooses canonical package/capability owners, applies migration rules, and marks conflicts before config activation.
- Materialize: ClawX installs, upgrades, copies, links, or verifies the physical package selected by resolution.
- Validate: ClawX verifies package manifests, dependencies, capability config, ownership uniqueness, and startup requirements.
- Activate: only resolved and validated capabilities enter final OpenClaw runtime config.
- Recover: failed upgrades, stale registrations, conflicts, and removed channels converge to a single diagnosable state with rollback or cleanup paths.
- Package: cleanup and pruning keep packaged artifacts small without deleting target runtime assets; macOS universal packages keep both x64 and arm64 native payloads.

First-stage priority is integration safety: single-owner capability resolution, active config guards, direct regression tests for migration cases, and explicit task specs for resolution, validation, and recovery work.

ClawX also bundles capability-only plugins under `resources/openclaw-plugins/` that provide no
channel. `clawx-openai-image` and `clawx-gemini-image` each register one OpenClaw
image-generation provider, but neither owns a fixed set of provider keys: at `register()` time,
each inspects `api.config.models.providers` and claims, as `aliases`, whichever keys host a
model of its own family (OpenAI Images vs. Gemini `generateContent`) — determined by model id,
never by parsing the key's name, since provider keys are generated by
`getOpenClawProviderKeyForType` and carry no stable meaning. This lets an account's own
`imageGenerationModel` ref resolve directly to the right plugin without ClawX creating a
provider entry, copying a key, or rewriting the ref. They still follow the same lifecycle as
channel plugins for materialization — declare via `openclaw.plugin.json`, materialize into
`~/.openclaw/extensions/`, activate through `plugins.entries` plus `plugins.allow` — but that
activation step (`ensureClawXImagePluginConfig` in
`electron/gateway/image-generation-plugin-resolution.ts`) only enables the plugin(s) an existing
`imageGenerationModel` ref actually needs; there is no per-account provider entry or stored key to
recover on removal. Resolution across the two plugins is model-family-driven and disjoint by
construction: a model belongs to at most one family, so the two plugins never claim the same
provider key.

`tokenjuice` is a third capability-only plugin, and the one that shows why materialization must
gate activation rather than follow it. It is the exec/bash output compactor behind the
"prompt optimization" setting, and OpenClaw 2026.7.1 removed it from its own package
(`"!dist/extensions/tokenjuice/**"`), promoting it to an *external* official catalog entry whose
`install.defaultChoice` is `"npm"`. A configured id is therefore something the kernel's startup
migration tries to install from the npm registry, and a packaged Electron app has no npm — so the
install fails, the config preflight throws, and the Gateway refuses to report ready. ClawX mirrors
the plugin from `@openclaw/tokenjuice` like a channel plugin (declare via `openclaw.plugin.json`,
materialize into `~/.openclaw/extensions/tokenjuice`, activate through `plugins.entries` plus
`plugins.allow`), registers it as path-owned in `TRUSTED_OFFICIAL_EXTENSION_PLUGINS` so the
kernel's official-install repair pass cannot route it back through npm, and writes the activation
entry only when the mirror is genuinely on disk — see `configured-plugin-install-precondition`.

Bundled WeCom patches must preserve account isolation: account-less desktop sessions may resolve a sole configured account, while genuinely ambiguous multi-account sessions remain blocked.
